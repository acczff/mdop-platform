# ADR-0004：多组织隔离与演进规划

- 状态：已采纳（仅架构规划，本轮不修改表结构）
- 日期：2026-11-16

## 背景

当前 MDOP 采用单组织假设（参见 [ADR-0002](ADR-0002-财务通过只读契约引用收发事实.md) 中的单组织财务基线及主数据表设计），所有仓库、物料、往来单位、单据与财务往来默认归属同一运营实体。随着产品面向多工厂、多法人或多独立核算事业部推广，平台需要原生支持多组织（Multi-Organization）数据隔离与权限控制。

## 备选方案

1. **一组织一库 / 一套独立实例（物理隔离）**：隔离最彻底，但部署、升级、跨组织协同与资源利用率成本随组织数线性放大。
2. **共享库 + 行级 `org_id` 隔离（逻辑多组织）**：保持模块化单体与统一运维拓扑，通过组织维度的主数据、单据归属与权限作用域实现隔离，支持跨组织受控协同。

## 决策与理由

选择方案 2（逻辑多组织，行级 `org_id` 隔离），并采用**分阶段演进**策略（本轮仅确立设计与迁移路径，**暂不向业务表添加 `org_id` 列**）：

1. **主数据与单据维度**：
   - 新增组织主表（如 `md_organization`，含 `id`、`code`、`name`、`status` 等）。
   - 核心主数据（仓库、库位、物料组织视图、供应商/客户组织视图、BOM）与业务单据（采购、销售、生产工单、WMS 收发存/流水、财务依据与往来）均显式归属 `org_id`。
   - 原全局唯一索引（如编码、单号）调整为 `(org_id, code)` / `(org_id, doc_no)` 复合唯一约束，避免不同组织间编码冲突。
2. **权限与作用域模型**：
   - 账号与角色分配支持组织作用域（`org_id`），仓库范围（`wms:warehouse:<id>`）收敛为所选组织下的仓库集合；系统管理员可按平台级或组织级分级授权。
   - 请求上下文（如 `CurrentActorProvider` / `OrganizationContext`）在认证后绑定当前操作组织，所有读写服务强制校验目标资源 `org_id` 与上下文一致，防止越权串读或串写。
3. **存量单组织数据迁移策略**：
   - Expand 阶段：创建默认组织（如 `DEFAULT` / `id = 1`），为相关表添加可空 `org_id` 列，并通过数据回填迁移将历史数据统一归属默认组织。
   - 验证阶段：应用层双写与只读校验确认无 `org_id IS NULL` 遗漏。
   - Contract 阶段：将 `org_id` 收紧为 `NOT NULL`，补充外键/复合索引并移除旧全局唯一索引。
4. **查询与索引影响**：
   - 列表、统计、库存余额、对账与 Outbox/Inbox 查询均需以 `org_id` 作为前置过滤条件，核心查询索引调整为以 `org_id` 为前导列（如 `(org_id, status, ...)`），防止全表扫描和跨组织数据泄露。
   - 库存对账脚本（`audit-inventory.sql`）与财务串行锁粒度（[ADR-0002](ADR-0002-财务通过只读契约引用收发事实.md)）需按 `org_id` 分组，消除不同组织间的写入锁竞争。

## 代价

- 几乎所有领域表、查询 SQL、唯一索引和权限校验都需要系统性改造与回归验证。
- 跨组织调拨、集团汇总或共享物料字典等高级场景需在后续单独建模，不能与基础隔离混做。

## 重新评估条件

- 客户明确要求物理独立数据库或独立合规域（数据驻留/跨境隔离），无法接受共享表逻辑隔离。
- 单个组织数据量或并发远超单 MySQL 实例容量，需要按组织分库分片。
