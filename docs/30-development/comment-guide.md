# 注释规范

> 类型：参考 | 状态：稳定 | 适用：0.1 开发分支 | 责任：平台组

## 原则

注释回答“**为什么**”，代码回答“**做什么**”。读者看完注释应知道规则的来源、边界与破坏后果，而不是这一行在赋值。

## 必须写

| 位置 | 写什么 | 例子（概念） |
|---|---|---|
| 跨模块契约 | 保证什么、谁调用、失败语义 | “采购只读契约；不写 WMS 表” |
| 业务规则 | 规则来源、边界、违反后果 | “数量不得超过通知剩余，防止超收” |
| 并发与锁 | 加锁顺序、为什么不能换序 | “先仓库后单据，避免与收货互锁” |
| 幂等 | 键的构成、重放与冲突判定 | “哈希绑定操作者与载荷” |
| 金额/数量 | 精度、舍入、单位 | “按行四舍五入到分” |
| 复杂 SQL | 业务意图、走哪个索引 | “按余额+时间倒序，走 ix_ledger_balance” |
| 迁移 | 目的、影响表、回滚方式 | “新增来源列，旧行默认值” |
| 临时方案 | 原因、替代计划、期限 | “模拟入口，正式接入后删除” |

## 不要写

- 逐行解释代码在做什么；
- 与字段名重复的说明；
- 变更日志式注释（版本库已有）；
- 注释掉的旧代码（直接删除，历史在 Git）；
- 过期 TODO（没有责任人与期限的）。

## 格式

- **类级**：一到三行，职责 + 关键约束。公共类必须有。
- **方法级**：只给公共契约、领域规则、复杂算法写；简单 getter/setter 不写。
- **行内**：只用于解释“反直觉”的一行，例如为什么先插入再锁行。
- **SQL**：复杂查询上方写业务意图与索引；简单单表查询不写。
- **语言**：业务解释用中文，标识符与框架名保留英文。

## 覆盖策略

不设“注释率”指标，设“关键路径全覆盖”：

1. 库存余额与流水写入
2. 加锁顺序与并发协调
3. 幂等键与重放
4. 结案与事实摘要
5. 权限与数据范围
6. 金额与精度

这六处必须有解释性注释；其余按需。评审时看“关键路径是否解释清楚”，不看注释行数。

## 反面与正面（概念对照）

| 场景 | 不推荐 | 推荐 |
|---|---|---|
| 锁 | “加锁” | “先锁仓库再锁单据：与收货提交保持同一顺序，避免死锁” |
| 幂等 | “校验幂等键” | “同键同载荷返回原结果；换键视为新请求，防止重复建单” |
| 精度 | “保留两位小数” | “按行四舍五入到分，避免汇总后再舍入产生分差” |
| SQL | “查询库存” | “只取非零余额并走 (warehouse_id,id)，避免全表排序” |
| 迁移 | “加字段” | “新增 production_order_id，允许为空以兼容历史行” |

## 审查清单

- [ ] 公共类有类级说明
- [ ] 关键路径的“为什么”写清楚
- [ ] 没有复述代码的注释
- [ ] 没有过期 TODO 与注释掉的代码
- [ ] SQL 注释说明了业务意图或索引
