# 项目结构与开源展示整理报告

## 结论与范围

当前代码具备有边界的 WMS 公共流程，适合按“模块化单体 + 可追溯库存 + 模拟外部协作”展示。影响新读者理解的主要问题是入口过长、阶段性状态重复、历史设计与实际目录混用、缺少统一源码与接口导航，以及首次权限初始化步骤不连续。

本次基于 `5dca76e` 整理 Git 管理的后端、前端、迁移、部署、脚本、CI 与文档。全仓文件清点及链接检查覆盖全部纳入版本管理的文档；实现分析以模块依赖、控制器、主要事务与认证入口、前端路由/客户端和现有测试为依据。**这是结构与可维护性审查，不是逐行安全审计、所有组合场景验证或生产认证。** 忽略目录中的本地配置、备份和运行日志不是开源交付内容。

## 已整理的问题

| 问题 | 处理 |
|---|---|
| 首页混合长期愿景、迭代日志和使用流程 | README 收敛为定位、能力/边界、启动摘要和导航；具体提交证据进入 [status](status.md) |
| 第一次管理员登录无法进入收货 | 补齐系统管理员→基础资料员→建仓→分配实际仓库→作业/审批分离的完整顺序 |
| 使用说明分散且缺少入口 | 建立 [文档中心](../README.md)、快速开始、公共业务演练、接口约定、架构阅读指南 |
| 设计目录和 Redis 用途易被当成现状 | 区分设计与实际：WMS 当前 receiving/inventory 包，JPA 与 JDBC 并存，Redis 尚无业务用途 |
| 页面对接与数据库结构难定位 | 自动生成 POM 依赖、页面、控制器和所有迁移的 [源码导航](../reference/source-index.md) |
| 多处“当前 75 项”等数字滞后 | 当前摘要指向有提交身份的版本记录；历史测试不重写为新结果 |
| 文档变更没有自动检查 | 增加本地链接/锚点与源码导航一致性检查，CI 独立 `Documentation verify`，失败阻止发布候选 |
| 对外贡献说明偏向个人环境 | 补全 fork/分支、按改动验证、Issue 复现模板、明确尚无许可证和安全报告渠道的实际边界 |

## 代码层面的保持与改进方向

| 现状 | 后续处理边界 |
|---|---|
| 事务、幂等、权限、固定精度和流水已有真实基础设施回归 | 保持现有业务不变量；文档整理不批量改写库存 SQL 或迁移 |
| 多个 Service 将 SQL、映射与业务规则放在同类；不同切片的 DTO 拆分程度不同 | 对具体功能改动时逐步拆出查询/映射，先保留事务入口和回归，不为统一外观增加空层级 |
| 收货、库存、领料等 Vue 页面较长，查询/表单/状态并置 | 在相应业务修改时提取组件或 composable；需要保留切仓、迟到响应、不确定写入保护，不机械抽成通用 CRUD |
| 主数据全局目录、模拟权限较宽 | 作为当前单组织演练边界明确展示；面向多组织或生产接入时另做权限设计 |
| 包级依赖、端到端浏览器流程未全部纳入 CI | 当前只承诺已有 Maven 约束和测试；需要时再补架构测试与稳定 E2E，不能宣称现有 CI 覆盖一切 |
| HTTP 接口没有机器可读完整 schema | 当前提供接口约定、示例及全部源码入口；未来需要 SDK/外部对接时再维护完整 OpenAPI 契约 |

## 正式开放复用前的剩余事项

1. **许可证暂不选择**：按维护者决定保留无 LICENSE 状态，不标注 MIT/Apache 或“可自由商用”。
2. 待依赖 PR 按序审批合并后，在最终 main 上运行全部 CI，更新版本记录；候选包不等于正式 Release。
3. 仓库可见性、私有漏洞报告、分支保护等 GitHub 设置需要维护者检查；本文不声称已启用，也不自动改变设置。
4. 当前工作树只使用模拟数据；正式发布前仍需单独核对全部历史、历史附件及依赖许可，本次链接/结构检查不替代密钥扫描和许可证审查。
5. Windows 是一键开发启动路径，Linux 验证由 CI 覆盖；其他平台完整首次启动与任意企业数据升级尚未验证。

后续优先修复阻碍现有公共流程或读者复现的缺口。运输短少核销、复杂企业规则、完整 IAM 和真实外部系统接入继续按独立范围确认。
