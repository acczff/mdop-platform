# R1 采购销售联合验收

本轮按[首轮规划 ERP-01—ERP-10](下一阶段业务规划.md#7-有限验收与停止条件)验收采购、销售数量履约和必要异常。业务基线为 `316a07c`（销售 PR #38），采购、销售在同一应用、同一个新建隔离数据库执行；本轮仅修复库存对账脚本的正式销售反馈误报，未扩展业务或迁移。分支 `acczff/erp-r1-acceptance` 的最终 CI 与审批状态见对应 PR 和[版本记录](status.md)。

R1 结束只表示两条数量主线达到首轮条件，不表示收付款、完整 ERP、生产部署或 R2 已完成。采购原料和销售成品在本轮是两条独立主线；成品由明确标识的模拟 MES/QMS 提供，不能据此宣称销售需求至生产采购的全链贯通，后者属于 R2/R4。

## 1. 同版本实操记录

2026-10-09，使用 Java 25、MySQL 8.4.10 和销售基线的应用 JAR，新建空库 `mdop_r1_qa`。Flyway 从零完成 32 个迁移、创建 66 张表。必要初始化只建立原料/成品仓、库位、供应商、客户、物料和职责分离账号，不预置采购或销售订单，不调用模拟 ERP 建单。

| 链路 | 本次事实及结果 |
|---|---|
| 正常采购 | 页面创建需求 PR-00000001（100 件），独立审批后页面转 PO-00000002；订单独立审批，页面安排 60+40，首批页面送达正式 WMS 通知 #1，第二批送达 #2；累计收货、合格上架各 100，尚欠 0，结案 `QUALIFIED` |
| 不合格退供 | 需求 PR-00000003 → PO-00000004；两批共 100，合格上架 80、不合格 20；退供申请前及批准后未实际交接时结案均 409；确认实际退供 20 后结案 `WITH_RETURNS`，重放同一确认不重复扣库 |
| 正常销售 | 页面创建 SO-00000001（100 件），独立审批；页面安排 60+40，首批页面送达 WMS #1，第二批送达 #2；预占/拣货不计已发，复核驳回后直接出库 409，重新拣货并异人复核后实际出库；两条流水 −60/−40，未发 0，页面确认数量结案 |
| 来源和守恒 | 采购来源为正式 ERP 安排，销售来源为 `MDOP_SALES`；正式销售模拟反馈数为 0；采购及销售三张订单 `closureMatches=true`；库存 47 项对账全部为 0 |

页面实操包括采购需求创建、转订单、两次到货安排、首批送达、结果查阅；销售订单创建、两次发货安排、首批送达、最终结案及恢复后查阅。独立审批、第二批送达、WMS 实物作业、QMS/MES 模拟输入、不合格退供场景通过受控隔离 HTTP API 执行。这里明确区分页面与接口证据，不声称本次每个动作均为浏览器实操。

## 3. 确认缺口及最小修复

影响 ERP-07/08：原 `scripts/audit-inventory.sql` 的 `sales_feedback` 无条件要求已出库销售有 `SalesOutboundConfirmed` Outbox。两笔正式销售按设计不发送模拟反馈，导致健康数据被报出 2 条差异，妨碍恢复验收。

修复后的规则：模拟来源已出库必须恰好一条反馈；模拟来源未出库、正式来源所有状态必须为零。不通过向正式业务补发模拟消息来消除误报，也不跳过全部销售检查。

- 新增 `ErpSalesTests.auditSeparatesFormalFactsFromSimulatorFeedback`：真实正式出库无模拟反馈应通过；注入错误模拟反馈应报错，恢复后通过。修改前实测断言失败（期望 0、实际 1）。
- 扩展 `SalesTests.completeFlowOnlyDeductsPhysicalStockAtShippingAndPublishesOnce`：正常模拟出库反馈通过；临时隐藏反馈时实际 SQL 必须报错，恢复反馈后通过。
- 两类测试直接执行仓库中的完整对账 SQL，不另写一份查询模拟脚本行为。仍保留 47 项检查，正式 ERP 数量/来源/结案由各履约服务及回归补充核验。

## 4. 停写备份与恢复

1. 三张订单完成后停止隔离应用；本次消息发布/消费关闭，没有外部系统写入。保留原库，不覆盖其他环境。
2. 按[发布包手册](../../deploy/release/RUNBOOK.md)调用 `scripts/release/database.mjs backup`，校验备份前后全库数据指纹相同，记录匹配应用 JAR、32 个迁移和 66 张表。
3. 调用 `restore` 恢复到另一个空库 `mdop_r1_restore`，工具验证恢复全库指纹与原快照一致。以相同 JAR 启动恢复库，重新登录，并读取两张采购和一张销售的原结案与来源。
4. 两库分别执行修正后的库存对账，47 项均为 0；恢复后的三个 `closureMatches` 均为 true。浏览器重新登录销售账号，核对 100 已发、0 未发和两条 60/40 来源及原结案时间。

## 5. 交付停止点

本轮交付为 R1 联合验收和一个对账缺口修复，PR 保留待统一审批；不自动合并、不升级日常数据库、不启动或重启 Docker Desktop。全量 CI 通过后按 ERP-01—ERP-10 收口 R1，下一独立闭环进入 R2 生产与物料基础，具体仍以七部分执行规格为准。

运输短少核销、采购付款、销售收款、客户退货、动态审批、真实外部接入与企业特定策略均不因验收而提前开发。
