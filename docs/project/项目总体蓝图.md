仓库聚合继续使用 JPA。收货切片与新增基础资料使用 Spring JdbcClient 和参数化 SQL，在同一 Spring 本地事务中明确实现累计数量条件更新、通知行锁、排序后的余额行锁和事务 Outbox；不引入新的持久化框架。相比全部使用 JPA，此选择让关键库存 SQL 与锁顺序更直接，但需要手工维护 SQL、映射与迁移，并通过真实 MySQL 集成测试保护事务和并发。WMS 仅通过 CatalogService 获取主数据规则，不直接访问其他模块的 Repository。未来形成更多聚合和查询场景时再评估是否抽取更细的持久化接口。

认证保留服务端 Session 和 CSRF，本轮切换数据库账号和固定角色分配；启动配置仅用于首次初始化与旧操作员导入，不把首版视为完整 IAM。消息切片已实现 Inbox/Outbox 与 RabbitMQ 可靠投递、ERP/QMS 模拟接收、重试、重放与本地对账。业务状态与 Inbox 同事务提交，发布网络请求不进入库存事务；真实系统对接仍待独立联调。设计取舍与验收见[消息接入与可靠反馈](./I2-I4消息接入与可靠反馈.md)。

## 1. 项目愿景

本项目模拟一家离散制造企业，从客户需求进入，到销售、计划、采购、生产、质量、仓储、配送、设备管理和经营分析的完整数字化过程。

项目不以“功能数量最多”为目标，而以以下结果为准：

- 业务流程能够形成端到端闭环。
- 关键数据正确、可追溯、可对账。
- 权限边界清晰，敏感操作可审计。
- 异常能够发现、定位、恢复和补偿。
- 代码具备清晰边界，可以测试、维护和持续演进。
- 系统具备标准化构建、部署、监控和回滚能力。
- 项目中的关键设计能够由项目负责人独立解释和取舍。

## 2. 项目定位

### 2.1 项目是什么

这是一个“统一平台 + 多个业务系统”的制造业企业应用集合体：

```text
制造业数字化运营平台
├─ 平台基础能力
├─ IAM 统一身份与权限
├─ MDM 主数据管理
├─ CRM 客户与销售
├─ ERP 订单、采购与结算
├─ APS 生产计划与排程
├─ MES 生产执行
├─ QMS 质量管理
├─ WMS 仓储管理
├─ TMS 运输配送
├─ EAM 设备资产与维修
├─ IoT 设备接入
└─ BI 数据分析
```

### 2.2 项目不是什么

- 不复制SAP、用友或大型MES的全部功能。
- 不实现完整财务总账、税务和薪资系统。
- 不在业务边界尚未稳定时拆成大量微服务。
- 不为展示技术名词而引入没有实际价值的中间件。
- 不一次性开发所有系统，而是沿核心业务链路逐步扩展。

## 3. 总体业务主线

第一条核心链路：

```text
客户建档
→ 销售订单
→ 生产需求
→ 生产计划
→ 生产工单
→ 工序与报工
→ 完工质检
→ 成品入库
→ 销售出库
→ 配送签收
→ 客户对账
```

第二条物料保障链路：

```text
生产需求
→ BOM展开
→ 物料需求
→ 采购申请
→ 采购订单
→ 供应商到货
→ 来料检验
→ 原料入库
→ 生产领料
```

第三条设备保障链路：

```text
设备建档
→ 点检与保养
→ 状态采集
→ 故障告警
→ 故障报修
→ 维修派工
→ 维修执行
→ 验收关闭
```

## 5. 架构原则

### 5.1 业务系统不等于微服务

业务上划分为多个系统，技术上先采用模块化单体：

```text
一个代码仓库
一个后端部署单元
一个数据库实例
多个边界明确的业务模块
```

模块必须遵守：

- 业务模块拥有自己的实体、应用服务和Repository。
- 其他模块不能直接访问该模块的Repository。
- 跨模块通过公开应用接口或领域事件协作。
- 公共模块只能放通用能力，不能成为业务代码垃圾桶。
- 数据库表按业务域归属，Flyway只有一个权威执行入口。

### 5.2 微服务演进条件

只有满足下列条件之一才考虑拆分：

- 模块需要独立部署或高频发布。
- 模块需要独立扩容或使用不同技术模型。
- 团队形成独立负责边界。
- 数据隔离、安全或合规要求明确。
- 单体已经产生经过测量的性能或维护瓶颈。

优先候选包括IAM、IoT、文件服务和通知服务。

### 5.3 数据原则

- 业务单据状态不能被任意修改。
- 关键数量、金额和库存变化必须可追溯。
- 跨系统只传递必要数据和业务事实。
- 核心写操作必须考虑事务、并发和幂等。
- 异步一致性必须具备重试、补偿和对账能力。
- 删除策略、时间、精度、编码和审计字段统一规范。

### 5.4 安全原则

- 使用Spring Security建立统一认证授权。
- Token必须具备可靠签名、有效期和失效机制。
- 后端执行接口权限和数据权限校验。
- 密码、密钥和生产配置不得硬编码。
- 关键操作必须记录操作者、对象、时间和结果。

## 7. 建设路线

### 7.0 当前执行边界：WMS 公共业务闭环

2026-10-07 确认推进原则：先完成一套可操作、可追溯、可对账的公共主流程及基本异常处理；具体企业的审批层级、作业策略和复杂异常，取得实际业务依据后单独迭代。以下范围约束当前排期。后续阶段与版本里程碑保留为长期能力目标，不要求为了结束 WMS 阶段提前补齐完整 IAM、ERP、MES 或全部仓储扩展。

#### 公共能力与环境规则

| 层次 | 内容 | 推进规则 |
|---|---|---|
| 公共业务事实与约束 | 有来源的业务单据、实物与库存记账对应、库存位置及状态、数量守恒、来源追溯、权限与审计、重复和并发安全 | 必须在主流程中成立，不能由企业配置关闭 |
| 当前已确认作业流程 | 现有收货、质检上架、预占、发料、退料、复核出库、盘点、冻结及调拨规则 | 按已确认范围验收；不把单批次、整单执行、固定双人审核等选择宣称为所有企业的统一规则 |
| 企业差异策略 | 审批层级、超收容差、FIFO/FEFO、替代料、超领、抽检/复检、货损责任、财务核销、设备协同等 | 有具体工作环境及验收依据后确认，不预建通用规则引擎，不持续追加为当前阶段门槛 |

#### 本阶段必须贯通的流程

| 流程 | 起点到终点 | 当前边界 |
|---|---|---|
| 采购入库 | 模拟 ERP 到货 → 分批收货 → 待检 → 模拟 QMS 判定 → 合格上架；不合格可申请、异人审批并确认退供 | 差异留痕；未进入后续处理的收货可按现有规则冲正 |
| 生产物料协同 | 模拟 MES 需求 → 原料预占 → 发至线边 → 依据 MES 结果记录消耗，或确认余料退回 → 反馈 | 发料保持企业总实存，实际消耗才减少；不计算 BOM、产量或工艺损耗 |
| 成品出入库 | 模拟 MES 完工需求 → 成品待检、判定、上架 → 模拟 ERP 出库需求 → 预占、拣货、异人复核、实际发出 → 反馈 | 完工需求为独立来源依据，不以原料消耗自动推算成品；不含运输签收和财务 |
| 库存运营 | 查询追溯、仓内移库、盘点审核、冻结解冻；跨仓申请 → 审批预占 → 发出转在途 → 分批实收完结 | 各次动作、库存变化和在途量可核对；不要求先实现所有库存异常处置 |

公共主流程完整不等于 MDOP 全平台订单到回款闭环完成。外部系统仍使用明确标识的模拟输入与反馈，真实系统接入另行验收。

#### 基本异常的最低要求

- 非法数量、超收、库存不足、失效状态、越权、自审及当前规则禁止的过期/冻结操作必须拒绝，不能留下部分记账。
- 重复提交、并发竞争、请求超时和迟到响应不能重复入账或串单；结果不确定时保留原请求并支持查证或原样重试。
- 消息失败保留重试、死信及有权限的人工重放；库存、流水、单据与反馈可对账，不以发布成功冒充下游已处理。
- 未实际完成的业务按既有规则撤销并释放占用；已有明确冲正或退货流程的业务保留原记录后纠正。没有已确认纠错规则的已完成业务禁止删除、覆盖或直接改余额。
- 尚不支持的运输短少、在途过期、货损等必须保留原单、已收与剩余在途量，明确显示阻断原因并可定位责任单据；不能伪造收齐、擅自核销或让用户误以为已完成。处置规则未确认时保留待处理，不要求本阶段自动解决所有异常。

#### 阶段完成标准与后续顺序

1. 按 [WMS 公共流程验收清单](WMS公共流程验收清单.md)将上述主流程、基本异常映射到实现、测试及 PR，逐项区分已实现、已验证、待审批与待部署。只修复会破坏这些要求的缺口，不用测试数量代替流程验收。
2. 在同一候选版本、隔离环境和明确角色下完成主流程演示与基本异常验收；库存、预占、生产归属和在途对账无无法解释的差异。验证升级、备份恢复及匹配版本回退说明，保留可复现步骤。
3. 统一当前契约、运行说明和已知限制；依赖 PR 经用户审批后再合并。日常库升级与真实环境上线另行安排，隔离验收不代表已经部署。
4. 范围与验收满足后结束本阶段，再选择下一阶段核心成果。用户/固定角色管理、管理员职责分离、CI 和发布恢复已经形成后续实现，具体代码与合并状态见[版本记录](status.md)；完整 IAM 与生产部署仍需独立确认，不能据此宣称已具备生产运行条件。

运输短少核销、调拨冲正、客户退货、报废、备件耗材领用、序列号、部分发料/发货和复杂质量处理均保留在后续需求中。本次不默认启动运输短少核销，也不把这些事项全部设为当前阶段完成前提。若验收发现其中某项确实阻断已确认主流程，应记录证据、影响及最小补充范围后再调整。

本节确定推进边界，不将未执行的验收、审批或部署标为完成。历史迭代验收记录继续保留，未来需求不自动获得实现或环境变更授权。

### 阶段0：新项目工程基线

目标：在独立仓库中从零建立可重复构建、测试和演进的企业级工程骨架。

- 创建独立Git仓库，旧项目只作为业务和技术参考，不复制旧代码与旧数据。
- 建立后端模块化单体骨架、Maven Wrapper和模块依赖规则。
- 建立前端pnpm工作区和管理端应用，预留共享包工作区入口但不提前创建空包。
- 建立开发、测试、生产配置框架。
- 建立Flyway空库初始化与迁移校验、Testcontainers测试基座和质量门禁。
- 建立MySQL、RabbitMQ、Redis本地基础设施编排。
- 建立统一启动、测试、构建和部署方式。

完成标准：新环境能够根据README启动；前后端基础工程可构建、可测试；数据库能从空库建立迁移历史并完成校验；旧项目未进入新仓库；模块边界和后续扩展方式明确。

### 阶段1：平台底座、IAM与MDM

- Spring Security认证授权
- 用户、组织、角色和数据权限
- 动态菜单和前端路由
- 操作审计
- 客户、供应商、产品、物料
- 工厂、车间、仓库、库区和库位
- 工序、设备、BOM基础模型

当前已确认实施切片：

- [I1.1仓库主数据方案](./I1.1仓库主数据方案.md)：先完成仓库定义、分类、查询、启停、受控修改、审计和错误闭环；暂不提前实施库区、库位、库存或完整 IAM。

完成标准：形成可信的安全底座和可被业务引用的主数据。

### 阶段2：订单到生产

- 客户销售订单
- 订单审核
- 生产需求
- 简单生产计划
- 生产工单
- 工序任务
- 报工和审核

完成标准：销售订单可以追踪到工单及实际生产进度。

### 阶段3：质量、入库与出库

- 完工质检
- 不合格处理和复检
- 成品入库
- 库存余额和流水
- 库存占用
- 拣货、复核、出库
- 并发安全、幂等和库存对账

完成标准：打通“销售订单→生产→质检→入库→出库”第一条端到端链路，并通过并发和重复请求测试。

### 阶段4：采购与原料保障

- BOM物料需求
- 采购申请和采购订单

- 来料检验
- 原材料入库
- 生产领料和退料

完成标准：生产工单能够追溯其原料来源与消耗。

### 阶段5：配送、签收与对账

- 配送任务
- 发运和运输节点
- 异常配送
- 客户签收
- 客户对账和回款状态

完成标准：打通订单到签收和对账的经营闭环。

### 阶段6：设备、维修与IoT

- 设备台账
- 点检和保养
- 故障报修与维修
- MQTT/TCP设备接入
- 状态采集和告警
- 指令下发、回执、超时、重试和审计

完成标准：业务系统能够根据设备事件创建或驱动维修流程，远程指令全链路可追踪。

### 阶段7：可靠性、分析与架构演进

- Outbox可靠事件
- MQ消费幂等、重试和死信
- 定时补偿和业务对账
- 结构化日志和链路追踪
- Prometheus与Grafana监控
- 性能测试和故障演练
- BI指标与经营看板
- 根据真实瓶颈决定是否拆分服务

完成标准：系统能够观测、恢复、对账、发布和回滚。

## 8. 企业级质量门槛

每个业务功能必须至少具备：

- 明确的业务背景和使用角色。
- 正常流程、异常流程和状态迁移。
- 接口权限和数据权限。
- 数据库约束、事务边界和并发策略。
- 幂等要求和重复提交处理。
- 操作日志和关键业务流水。
- 单元测试与集成测试。
- 可验收的前端操作闭环。
- 对应接口、业务和故障排查文档。

核心链路额外要求：

- 支持端到端自动化测试。
- 支持失败回滚、补偿或人工处理。
- 支持通过业务单号追踪完整链路。
- 支持数据对账和差异定位。

## 9. 测试与交付体系

### 9.1 测试分层

- 单元测试：状态机、计算、权限和业务规则。
- 集成测试：Controller、Service、Repository及事务。
- 基础设施测试：使用Testcontainers验证MySQL、Redis和RabbitMQ。
- API测试：正常、异常、越权、重复及并发场景。
- 端到端测试：覆盖订单到出库等核心业务链路。
- 性能测试：库存扣减、报工、设备上报等重点接口。

### 9.2 交付流水线

```text
提交代码
→ 静态检查
→ 自动编译
→ 自动测试
→ 构建镜像
→ 部署测试环境
→ 数据库迁移
→ 冒烟测试
→ 人工确认
→ 生产发布或回滚
```

- 未来重新评估条件

## 11. 学习驱动机制

本项目同时是学习系统。学习顺序遵循：

```text
选择业务任务
→ 识别知识缺口
→ 学习必要原理
→ 完成实现
→ 编写测试验证
→ 形成文档和复盘
→ 用自己的语言讲解
```

每个迭代必须产生五类成果：

1. 可运行代码。
2. 自动化测试。
3. 业务或技术文档。
4. 一次演示或验收记录。
5. 一篇个人复盘。

禁止用观看视频时长、阅读页数或生成笔记数量代替项目成果。

## 14. 蓝图维护规则

- 本文档是项目最高层级的范围和方向依据。
- 新系统、新中间件和重大架构调整必须先更新蓝图或新增ADR。
- 详细需求、设计和学习笔记以后按实际迭代逐步建立，禁止提前批量生成空洞文档。
- 每完成一个版本里程碑，重新评估范围、风险和下一阶段优先级。
- 如果实际业务证据与本蓝图冲突，以真实业务问题为准，并记录调整原因。
